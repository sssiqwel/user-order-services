# Отчёт по лабораторной работе

## Интеграционное тестирование методом «большого взрыва»

## Цель работы

Изучить метод интеграционного тестирования «большого взрыва», применить его на учебном проекте, найти и записать дефекты, а также разобраться, какие проблемы возникают при таком подходе.

## Задание

1. Ознакомиться с проектом, его структурой и модулями.
2. Применить метод «большого взрыва», то есть интегрировать все модули сразу, в один этап.
3. Провести тестирование и записать найденные дефекты и аномалии.
4. Составить отчёт по результатам.

## 1. Теоретическая часть

Метод «большого взрыва» (big bang) — это способ интеграционного тестирования, при котором все модули системы собирают вместе за один раз и тестируют уже готовую систему целиком. Связки модулей по отдельности заранее не проверяются. Обычно так делают в конце разработки, когда все модули уже написаны.

Плюсы метода:

- не нужно писать заглушки и драйверы для недостающих модулей;
- сразу видно, работает ли система в целом.

Минусы метода:

- если что-то не работает, сложно понять, в каком модуле ошибка;
- ошибки находятся поздно, только когда собрана вся система;
- метод подходит в основном для небольших проектов, где мало модулей.

Для сравнения, при инкрементальном тестировании (сверху вниз или снизу вверх) модули подключают по одному и проверяют систему после каждого шага. Так проще найти, какой модуль сломал работу.

## 2. Описание проекта

В задании в качестве примера указан проект eShopOnWeb. Это демонстрационный интернет-магазин от Microsoft на ASP.NET Core. В нём есть каталог товаров, корзина, заказы и учётные записи покупателей (Identity). Если тестировать его «большим взрывом», нужно запустить все части сразу и проверить сценарий «выбрать товар → положить в корзину → оформить заказ».

Я применил метод на учебном проекте `user-order-services`, который мы делали раньше в рамках курса. Он устроен похоже на eShopOnWeb, только проще: есть сервис пользователей и сервис заказов, и заказ зависит от пользователя, так же как в eShopOnWeb заказ зависит от покупателя.

| eShopOnWeb | user-order-services |
|---|---|
| Identity / покупатель (Buyer) | Users API |
| Заказы и корзина (Order, Basket) | Orders API |
| Доступ к данным (Infrastructure) | хранилища `storage.py` и HTTP-клиент `users_client.py` |
| Web и PublicApi | `main.py` в каждом сервисе |

### 2.1. Модули проекта

Проект состоит из двух сервисов на FastAPI.

**Users API** (порт 8001) — работа с пользователями:

- `models.py` — модели и проверка данных (имя, email);
- `storage.py` — хранение пользователей в памяти, при запуске есть два пользователя: Анна (id=1) и Пётр (id=2);
- `auth.py` — проверка Bearer-токена при создании пользователя;
- `main.py` — эндпоинты `/health`, список пользователей, пользователь по id, создание пользователя.

**Orders API** (порт 8002) — работа с заказами:

- `models.py` — модели заказа и данных пользователя внутри заказа;
- `storage.py` — хранение заказов в памяти;
- `auth.py` — проверка токена при создании заказа;
- `users_client.py` — HTTP-клиент, который запрашивает пользователя в Users API;
- `main.py` — эндпоинты `/health`, список заказов, заказ по id, создание заказа.

Схема взаимодействия:

```
клиент ──► Orders API ──GET /api/v1/users/{id}──► Users API
```

Когда создаётся или читается заказ, Orders API каждый раз запрашивает данные пользователя в Users API. Если пользователя нет, возвращается 404, если Users API недоступен — 503.

Все данные хранятся в памяти. Поэтому если перезапустить Users API, в нём снова останутся только два стартовых пользователя, а созданные пользователи пропадут.

## 3. Ход работы

### 3.1. Применение метода

По методу «большого взрыва» я не проверял модули по отдельности и не использовал заглушки. В тестах оба сервиса запускаются одновременно, после чего тесты отправляют HTTP-запросы к уже собранной системе.

Тесты находятся в файле `tests/test_big_bang.py`. Сервисы для них запускаются на портах 28001 и 28002, чтобы не мешать обычным тестам. Для тестов, где нужно перезапустить или выключить Users API, поднимается отдельная пара сервисов.

Команда для запуска:

```bash
make test-bigbang
```

### 3.2. Тестовые сценарии

| ID | Что проверяется | Ожидаемый результат |
|---|---|---|
| BB-01 | Полный сценарий: health обоих сервисов, создание пользователя, создание заказа, чтение заказа и списка заказов | Все запросы успешны (200/201), в заказе есть данные пользователя, есть заголовки `Location`, `X-Request-ID`, `X-User-Service-Time-Ms` |
| BB-02 | Ошибки: заказ несуществующему пользователю, запрос без токена, неверный токен, неверные данные, несуществующий заказ | 404, 401, 401, 422, 404 |
| BB-03 | Время ответа списка заказов по сравнению с одним заказом | Время списка не должно сильно расти от количества заказов |
| BB-04 | Создаём заказы двум пользователям, перезапускаем Users API (один пользователь пропадает), запрашиваем список заказов | 200, в списке есть хотя бы заказ пользователя с id=1 |
| BB-05 | Создаём пользователя и заказ, перезапускаем Users API, запрашиваем этот заказ | Заказ возвращается или выдаётся отдельная понятная ошибка |
| BB-06 | Выключаем Users API и проверяем `/health` у Orders API | Должно быть видно, что зависимость недоступна |
| BB-07 | Передаём свой `X-Request-ID` в запросах к Orders API | В ответе возвращается тот же `X-Request-ID` |

## 4. Результаты тестирования

Первый запуск тестов:

```
test_bb_01_all_modules_together_happy_path          PASSED
test_bb_02_error_paths_on_fully_assembled_system    PASSED
test_bb_03_n_plus_one_user_fetches_on_list          PASSED
test_bb_04_list_orders_fails_entirely_if_one_user…  FAILED
test_bb_05_get_order_masks_missing_user_as_order…   FAILED

test_bb_07_request_id_propagates_across_services    PASSED

```

Всего 7 тестов: 5 прошли, 2 упали. Основной сценарий (BB-01) работает, то есть если ничего не перезапускать, система выглядит полностью рабочей. Ошибки появились только в тестах с перезапуском Users API.

Тесты BB-03 и BB-06 прошли, но в них я тоже заметил проблемы, поэтому записал их как аномалии.

После этого я пометил упавшие тесты BB-04 и BB-05 как `xfail` (ожидаемое падение из-за известного дефекта). Теперь результат запуска такой: `5 passed, 2 xfailed`. Если дефекты исправят, эти тесты начнут проходить, и pytest об этом сообщит.

Результаты первого запуска сохранены в `reports/pytest-bigbang-first-run.txt`.

## 5. Найденные дефекты и аномалии

### Дефект 1 (BB-04). Список заказов не открывается, если пропал один пользователь

**Серьёзность:** высокая

**Шаги:**

1. Создать заказ для пользователя с id=1.
2. Создать нового пользователя (получил id=3) и заказ для него.
3. Перезапустить Users API. Пользователь с id=3 пропадает, пользователь с id=1 остаётся.
4. Отправить `GET /api/v1/orders`.

**Ожидаемый результат:** 200 и список заказов, в котором есть хотя бы заказ пользователя с id=1.

**Фактический результат:** `404 {"detail": "User 3 not found"}`. Весь список не возвращается.

**Комментарий:** из-за одного «битого» заказа не работает весь список. По ответу непонятно, где именно ошибка: в Users API, в HTTP-клиенте или в Orders API. На самом деле ответ формирует Orders API, хотя текст похож на ответ Users API.

### Дефект 2 (BB-05). Существующий заказ возвращает ошибку «пользователь не найден»

**Серьёзность:** высокая

**Шаги:**

1. Создать пользователя и заказ для него.
2. Перезапустить Users API.
3. Отправить `GET /api/v1/orders/1`.

**Ожидаемый результат:** заказ возвращается, или приходит отдельная ошибка, по которой понятно, что заказ есть, но пользователь недоступен.

**Фактический результат:** `404 {"detail": "User 3 not found"}`, при этом нет заголовка `X-User-Service-Time-Ms`.

**Комментарий:** клиент получает 404 и может подумать, что заказа нет, хотя он есть. Получается, что «нет заказа» и «нет пользователя» выглядят почти одинаково.

### Аномалия 1 (BB-03). Лишние запросы к Users API при получении списка заказов

При запросе списка заказов Orders API отправляет запрос в Users API для каждого заказа отдельно, даже если у всех заказов один и тот же пользователь.

- один заказ: 0,86 мс на запрос к Users API;
- список из 5 заказов: 3,68 мс.

Время растёт примерно пропорционально количеству заказов. На маленьком проекте это не критично, но при большом количестве заказов будет заметно.

### Аномалия 2 (BB-06). Health показывает, что всё в порядке, когда Users API выключен

При выключенном Users API:

- `GET /health` у Orders API возвращает 200 `{"status": "ok"}`;
- `GET /api/v1/orders/{id}` и `GET /api/v1/orders` возвращают 503.

То есть по health-проверке кажется, что сервис работает, хотя заказы получить нельзя. Это спорный момент, потому что health часто специально проверяет только сам сервис, но для мониторинга это может ввести в заблуждение.

### Другие замечания

- У каждого сервиса своё хранилище в памяти, поэтому после перезапуска одного сервиса данные двух сервисов перестают совпадать.
- Orders API не сохраняет данные пользователя вместе с заказом, поэтому без Users API заказ вообще нельзя показать.
- Файл `auth.py` одинаковый в двух сервисах. Если токены в них будут разными, ошибка 401 появится сразу в двух местах.

## 6. Проблемы метода «большого взрыва»

**1. Сложно найти причину ошибки.** Оба дефекта дали одинаковый ответ: `404 User 3 not found`. По нему нельзя сразу понять, какой модуль виноват. Чтобы разобраться, мне пришлось смотреть код нескольких файлов: хранилища пользователей, HTTP-клиента и обработчиков в Orders API.

**2. Основной сценарий проходит, и кажется, что всё работает.** Если бы я проверил только BB-01 и BB-02, можно было бы решить, что интеграция прошла успешно. Ошибки нашлись только в тестах с перезапуском Users API, которые пришлось придумывать отдельно.

**3. Много комбинаций для проверки.** Когда все модули работают одновременно, нужно учитывать много состояний сразу: есть ли токен, есть ли пользователь, доступен ли Users API, был ли перезапуск. Метод не подсказывает, в каком порядке это проверять.

**4. Ошибки находятся поздно.** Пока все модули не собраны, тестирование ничего не показывает. Ошибку в HTTP-клиенте можно было бы найти раньше, если бы Orders API сначала проверялся с заглушкой вместо Users API.

Если бы я тестировал инкрементально, например сначала Orders API с заглушкой Users API, которая возвращает 404 для одного пользователя, то сразу было бы видно, что ошибка в обработке списка заказов в Orders API.

В моём проекте всего два сервиса, но даже здесь искать причину было неудобно. В eShopOnWeb модулей гораздо больше (каталог, корзина, заказы, Identity, база данных, веб-интерфейс), и там такая же ошибка 404 могла бы быть вызвана гораздо большим числом причин.

## Вывод

В ходе лабораторной работы я изучил метод интеграционного тестирования «большого взрыва» и применил его на проекте Users API + Orders API. Все модули были запущены одновременно, без заглушек, и проверялись как одна система.

Было написано 7 тестов. Основной сценарий работы прошёл успешно, но были найдены 2 дефекта (список заказов падает целиком, если пропал один пользователь; существующий заказ возвращает 404) и 2 аномалии (лишние запросы к Users API и health, который не показывает недоступность Users API).

Работа показала главный недостаток метода: оба дефекта дали одинаковую ошибку, и по ней было сложно понять, в каком модуле проблема. Я считаю, что метод «большого взрыва» подходит для небольших проектов как финальная проверка того, что система вообще работает, но для поиска и исправления ошибок лучше использовать инкрементальное тестирование.

## Как запустить

```bash
make install
make test-bigbang
```

Чтобы увидеть дефекты как обычные упавшие тесты:

```bash
.venv/bin/python -m pytest tests/test_big_bang.py --runxfail
```
