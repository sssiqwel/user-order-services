## 2. Суть метода «большого взрыва»

Метод «большого взрыва» (big bang integration) — это стратегия, при которой **все разработанные модули объединяются одновременно** и тестируются только как готовая система. Отдельные связки модулей заранее не проверяются. Интеграция откладывается на конец разработки.

Свойства метода:

| Свойство | Следствие |
|---|---|
| Одновременная интеграция | Сразу видно, «живёт» ли система целиком |
| Нет промежуточных сборок | Экономия на драйверах, заглушках и поэтапных стендах |
| Высокий риск ошибок | Дефект проявляется только на полной сборке |
| Сложность диагностики | По одному ответу API неясно, какой модуль виноват |
| Уместность | Приемлем для небольших систем с малым числом модулей |

Отличие от инкрементальных стратегий (сверху вниз, снизу вверх, «сэндвич»): там модули подключают по одному и после каждого шага прогоняют узкий набор проверок. В «большом взрыве» такого шага нет — либо вся система, либо ничего.

## 3. eShopOnWeb как типовой пример и отображение на учебный проект

eShopOnWeb — демонстрационный интернет-магазин Microsoft. Именно на таких системах в курсе показывают, как «большой взрыв» выглядит на практике: витрина, каталог, корзина, заказ и идентификация поднимаются сразу.

### 3.1. Модули eShopOnWeb

```
eShopOnWeb
├── ApplicationCore     сущности и сервисы предметной области
│   ├── CatalogItem, CatalogBrand, CatalogType
│   ├── Basket, BasketItem
│   ├── Order, OrderItem
│   └── Buyer + интерфейсы репозиториев и сервисов
├── Infrastructure      EF Core, ASP.NET Identity, почта
├── Web                 MVC-витрина (каталог → корзина → оформление)
├── PublicApi           HTTP API каталога
└── BlazorAdmin         админка
```

Если применить «большой взрыв» к eShopOnWeb буквально, стенд выглядит так: поднимаются Identity, каталог, корзина, заказы, инфраструктура БД и Web, после чего тестировщик проходит сценарий «найти товар → положить в корзину → оформить заказ» **одним этапом**, без предварительной проверки `BasketService` отдельно от репозитория и без проверки `OrderService` отдельно от Identity.

Именно эта схема перенесена на учебный вариант курса.

### 3.2. Соответствие модулей

Учебный проект `user-order-services` — компактный аналог той же интеграции: сервис заказов синхронно ходит в сервис пользователей, как в eShopOnWeb заказ и корзина опираются на покупателя (Buyer / Identity).

| eShopOnWeb | user-order-services | Роль на полной сборке |
|---|---|---|
| Identity / Buyer | `users_service` (models, storage, auth, API) | Кто покупатель |
| Order / Basket | `orders_service` (models, storage, auth, API) | Что заказано |
| Infrastructure (доступ к данным и внешние вызовы) | `users_service/app/storage.py`, `orders_service/app/storage.py`, `users_client.py` | Память процесса + HTTP |
| Web / PublicApi | FastAPI `main.py` обоих сервисов | Внешний контракт |
| Заголовок корреляции запроса | `X-Request-ID` | Сквозная трассировка |

Модулей немного, поэтому метод формально уместен. Цель работы — показать, что даже на маленькой системе диагностика уже страдает.

## 4. Структура и модули учебного проекта

Система состоит из двух процессов, которые в «большом взрыве» стартуют **вместе**, без заглушек.

```
клиент
  │
  ├─ HTTP ──► Users API  :8001 / :28001
  │              ├── auth.require_token
  │              ├── models.UserIn / User
  │              ├── storage.UserStorage   (память + 2 seed-пользователя)
  │              └── middleware X-Request-ID
  │
  └─ HTTP ──► Orders API :8002 / :28002
                 ├── auth.require_token
                 ├── models.OrderIn / Order / UserSnapshot
                 ├── storage.OrderStorage
                 ├── users_client.get_user  ──HTTP GET /api/v1/users/{id}──► Users API
                 └── middleware X-Request-ID
```

### 4.1. Модули Users API

| Модуль | Файл | Ответственность |
|---|---|---|
| Контракт | `users_service/app/models.py` | Валидация имени и email, запрет лишних полей |
| Хранилище | `users_service/app/storage.py` | In-memory словарь, уникальность email, seed (Анна, Пётр) |
| Авторизация | `users_service/app/auth.py` | Bearer-токен на POST |
| API | `users_service/app/main.py` | `/health`, список, получение, создание, `X-Request-ID` |

### 4.2. Модули Orders API

| Модуль | Файл | Ответственность |
|---|---|---|
| Контракт | `orders_service/app/models.py` | `user_id`, `item`, `quantity`, вложенный `UserSnapshot` |
| Хранилище | `orders_service/app/storage.py` | In-memory заказы, без снимка пользователя |
| Авторизация | `orders_service/app/auth.py` | Тот же Bearer-токен |
| HTTP-клиент | `orders_service/app/users_client.py` | Вызов Users API; 404 и 503 |
| API | `orders_service/app/main.py` | Создание/чтение с `enrich_order`, заголовок времени вызова |

Точка интеграции одна, но на ней сходятся сразу несколько модулей: валидация входа, токен, запись заказа, HTTP-клиент, хранилище пользователей, разбор ответа, сборка `UserSnapshot`. Именно поэтому «большой взрыв» здесь показателен: любой из этих модулей может дать один и тот же внешний симптом.

## 5. Как метод был применён

Инкрементальный стенд (сначала Users, потом клиент с заглушкой, потом Orders) **не собирался**. Оба сервиса стартовали одним шагом.

Практическая реализация — `tests/test_big_bang.py`:

- фикстура `bang` поднимает Users API и Orders API на портах `28001` и `28002` **одновременно**;
- фикстура `fresh_bang` даёт чистую пару процессов для разрушающих сценариев (рестарт и останов Users);
- заглушек, моков и подмены `users_client` нет;
- тесты видят только HTTP собранной системы.

Команды:

```bash
make test-bigbang
# то же самое:
.venv/bin/python -m pytest tests/test_big_bang.py -v --tb=short
```

Это и есть «один этап»: либо оба модуля живы и связаны реальным HTTP, либо сценарий не выполняется.

## 6. Тестовые сценарии на полной сборке

Сценарии специально не изолируют модули. Каждый из них бьёт по уже склеенной системе.

### BB-01. Сквозной happy path (все модули сразу)

| Поле | Содержание |

## 8. Выявленные дефекты и аномалии

### BB-04. Каскадный отказ списка заказов — критический

**Как проявился.** После рестарта Users API в хранилище снова только seed-пользователи с id 1 и 2. Заказ для Анны (id=1) остался, заказ для пользователя id=3 остался в Orders, но самого пользователя уже нет.

**Фактический ответ:**

```http
GET /api/v1/orders
HTTP/1.1 404
{"detail": "User 3 not found"}
```

**Почему это дефект.** Список — операция чтения множества. Один «битый» элемент не должен обнулять выдачу. Ожидалось HTTP 200 и заказ пользователя id=1 в массиве.

**Почему «большой взрыв» не помогает локализовать причину.** Один и тот же 404 могут дать:

1. `UserStorage.get` — пользователя нет после рестарта;
2. `users_client.get_user` — любой 404 Users превращается в `UserServiceError(404)`;
3. `enrich_order` — исключение сразу становится HTTPException;
4. `list_orders` — цикл без изоляции ошибки по элементу.

Без чтения кода и без поэтапного отключения модулей нельзя выбрать виновника. Сообщение «User 3 not found» выглядит как ответ Users API, хотя его сформировал Orders API.

### BB-05. Маскировка пропажи пользователя под 404 заказа — критический

**Как проявился.** Заказ с id=1 в Orders существует. После рестарта Users:

```http
GET /api/v1/orders/1
HTTP/1.1 404
{"detail": "User 3 not found"}
```

Заголовка `X-User-Service-Time-Ms` нет: исключение выбрасывается до `attach_timing`.

**Почему это дефект.** Клиент не отличает «заказа нет» (`Order {id} not found`) от «заказ есть, пользователь исчез». Для витрины в духе eShopOnWeb это аналог ситуации «заказ в истории есть, а покупатель из Identity пропал» — страница истории заказов должна показать заказ, а не «не найдено».

**Диагностика.** Снова один код 404. Возможные виновники: storage Users, клиент, `get_order`, отсутствие сохранённого снимка пользователя в `StoredOrder`. Метод не сужает круг.

### BB-03. N+1 вызовов Users API — средний

На полной сборке `GET /orders` вызывает `get_user` **для каждого** элемента. Замер заголовка:

- один заказ: **0,86 мс**;
- список из 5: **3,68 мс** (примерно пропорционально N).

На двух сервисах это ещё терпимо. На eShopOnWeb с корзиной из десятков позиций такой же паттерн (заказ → покупатель построчно) уже дал бы заметную задержку. «Большой взрыв» аномалию увидел, но не отделил её от функциональных 404: все симптомы сыплются из одного прогона.

### BB-06. Liveness не показывает поломку интеграции — средний

При остановленном Users API:

| Запрос | Результат |
|---|---|
| `GET /health` Orders | **200** `{"status":"ok"}` |
| `GET /orders/{id}` | **503** |
| `GET /orders` | **503** |

Сервис «жив», интеграция мертва. Для мониторинга это ложно-зелёный сигнал. Тест зафиксировал факт; как дефект контракта `/health` он спорный (часто liveness специально не трогает зависимости), поэтому в pytest он проходит, а в каталог аномалий попадает.

### Прочие наблюдения на полной сборке (не падения тестов)

1. **Два независимых in-memory storage.** Рестарт одного сервиса сразу делает данные другого лживыми. В eShopOnWeb ту же роль играет рассинхрон Identity DB и Orders DB.
2. **`StoredOrder` не хранит снимок пользователя.** Обогащение всегда живое. Нет деградации «показать хотя бы то, что сохранили».
3. **Дублирование `auth.py`.** Два модуля с одним токеном по умолчанию. Расхождение `API_TOKEN` на полной сборке дало бы 401 сразу на двух границах — снова без указания, какой копии auth это касается.
4. **Happy path маскирует дыры.** BB-01 зелёный, если не делать рестарт. Метод создаёт ложное ощущение готовности.

## 9. Проблемы метода, которые показал этот прогон

### 9.1. Сложность диагностики

Главный тезис метода подтвердился буквально. Оба падения — HTTP 404 с текстом `User 3 not found`. По внешнему симптому нельзя ответить:

- это Users не нашёл запись;
- это Orders неправильно пробросил ошибку;
- это storage заказов хранит «осиротевший» `user_id`;
- это `list_orders` не умеет пропускать битый элемент.

Инкрементальный подход локализовал бы быстрее: проверка Users после рестарта (пользователь 3 отсутствует — ожидаемо), проверка Orders со stub Users (заказ читается), проверка связки (ошибка именно в `enrich_order` / отсутствии изоляции в цикле).

### 9.2. Высокий риск «всё зелёное, пока не тронули край»

Пять тестов из семи зелёные, включая полный happy path. Если бы набор ограничился BB-01 и BB-02, отчёт сказал бы «интеграция успешна». Дефекты вылезли только на рестарте зависимости — типичный для «большого взрыва» слепой угол: тестируют счастливый путь собранной системы и не видят контракт при частичном отказе.

### 9.3. Комбинаторный взрыв состояний

На полной сборке одновременно живы auth, два storage, клиент, валидация, middleware. Число комбинаций (токен × наличие пользователя × доступность Users × непустой список заказов × рестарт) растёт быстро. Метод не даёт каркаса, в каком порядке эти комбинации включать. Пришлось сознательно писать разрушающие сценарии, иначе дефекты BB-04 и BB-05 остались бы ненайденными.

### 9.4. Ложное чувство «маленький проект — можно взрывать»

Учебная система меньше eShopOnWeb: два сервиса, нет БД, нет UI. Тем не менее локализация уже требует чтения нескольких файлов. На eShopOnWeb (Web + Identity + Catalog + Basket + Order + EF) тот же 404 на странице заказа мог бы означать пропавшего Buyer, сломанный `OrderService`, ошибку Razor Page или сбой SQL. Вывод: «подходит для небольших проектов» — не «безопасен», а «ещё можно пережить», и то при наличии хотя бы нескольких негативных сценариев на полной сборке.

### 9.5. Нет промежуточного регресса

Пока модули не склеены, «большой взрыв» не даёт сигналов. Ошибка в `users_client` (неверный URL, таймаут, разбор JSON) всплывает только в конце. Инкрементальная сборка поймала бы её на шаге «Orders + заглушка Users» или «Orders + реальный Users, без UI».

---

## 10. Сравнение с инкрементальной интеграцией (на тех же дефектах)

| Дефект | Большой взрыв | Если бы модули подключали по шагам |
|---|---|---|
| BB-04 каскадный 404 | Симптом: «список заказов не работает». Виновник неясен | Шаг «list_orders + stub get_user, stub кидает 404 на id=3»: сразу видно отсутствие try/except в цикле |
| BB-05 путаница 404 | Симптом совпадает с «нет заказа» | Шаг «get_order при живом storage и 404 от Users»: видно, что код и текст ошибки не про заказ |
| BB-03 N+1 | Видно по заголовку времени, но тонет среди 404 | Шаг «list_orders + счётчик вызовов stub»: N вызовов на N заказов, без остальной системы |
| BB-06 health | Зафиксировали, потому что специально остановили Users | Шаг «Orders без Users»: health vs 503 сравниваются изолированно |

Для eShopOnWeb инкремент выглядел бы так: сначала ApplicationCore + фейковый репозиторий, затем Infrastructure/EF, затем Identity, затем Web. «Большой взрыв» пропускает эти ступени и оставляет отладку на момент, когда уже запущено всё.

## 11. Выводы

1. Метод «большого взрыва» применён к учебному аналогу eShopOnWeb: все модули Users и Orders подняты одновременно, без заглушек, тесты идут только против полной сборки (`tests/test_big_bang.py`).
2. Базовый сквозной сценарий (BB-01, BB-02, BB-07) проходит. На этом метод создаёт впечатление успешной интеграции — типичная ловушка.
3. На той же сборке выявлены **два критических дефекта** (каскадный 404 списка заказов; маскировка пропавшего пользователя под 404 заказа) и **две аномалии** (N+1 вызовов, health без проверки зависимости).
4. Оба критических дефекта имеют **один внешний симптом** (`404 User 3 not found`). Это прямая демонстрация главной слабости метода: высокая стоимость локализации.
5. Для небольшого проекта метод допустим как **финальная дымовая проверка** «система вообще встаёт». Как единственная стратегия интеграции он недостаточен: крайние состояния (рестарт, частичный отказ) либо не проверяются, либо проверяются слишком поздно и слишком непрозрачно.
6. Практическая рекомендация: оставить прогон полной сборки (big bang smoke), но дефекты вроде BB-04/BB-05 закрывать инкрементально — изоляция ошибки в `list_orders`, сохранённый снимок пользователя, раздельные коды «нет заказа» / «нет пользователя», readiness отдельно от liveness.

## Приложение А. Как воспроизвести

make install

- `reports/pytest-bigbang-first-run.xml`
