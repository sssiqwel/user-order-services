## 2. Свой вариант: требования к системе

Система состоит из двух микросервисов.

| Сервис | Порт | Назначение |
|---|---|---|
| Users API | `8001` | Создание и получение пользователя |
| Orders API | `8002` | Создание и получение заказа; при этом запрашивает пользователя в Users API по `user_id` |

```
клиент ──► Orders API ──HTTP GET /api/v1/users/{id}──► Users API
                │
                └── 201/200 + данные пользователя
                    404 если пользователя нет
                    503 если Users API недоступен
```

### 2.1. Функциональные требования

**Users API**

- `GET /health` — сервис жив.
- `GET /api/v1/users` — список пользователей.
- `GET /api/v1/users/{id}` — пользователь по id; 404, если нет; 422 при невалидном id.
- `POST /api/v1/users` — создать пользователя (нужен Bearer-токен).
  - успех: 201 + заголовок `Location`;
  - без токена / неверный токен: 401;
  - email уже занят: 409;
  - невалидное тело: 422.
- `name`: 1–100 символов, не из одних пробелов, обрезаются края.
- `email`: нормализуется к нижнему регистру, уникален.
- Неизвестные поля запрещены. `id` назначает сервер.

**Orders API**

- `GET /health` — сервис жив.
- `GET /api/v1/orders` — список заказов; в каждом заказе вложенный `user` из Users API.
- `GET /api/v1/orders/{id}` — заказ по id с актуальными данными пользователя.
- `POST /api/v1/orders` — создать заказ (нужен Bearer-токен). Перед записью сервис вызывает `GET {USER_SERVICE_URL}/api/v1/users/{user_id}`.
  - успех: 201 + `Location` + вложенный `user`;
  - пользователя нет: 404, заказ **не** создаётся;
  - Users API недоступен / таймаут / 5xx: 503, заказ **не** создаётся;
  - без токена: 401;
  - невалидное тело: 422.
- `item`: непустая строка; `quantity`: 1–1000; `user_id` ≥ 1.

### 2.2. Нефункциональные и сквозные требования

- Изменяющие запросы требуют `Authorization: Bearer secret-token`.
- Каждый ответ содержит `X-Request-ID` (эхо клиентского или сгенерированный UUID).
- Ответы Orders API, которые ходили в Users API, содержат `X-User-Service-Time-Ms`.
- Межсервисный вызов должен укладываться в SLO: **< 500 мс** (заголовок), весь HTTP-ответ — **< 1000 мс**.
- Таймаут вызова Users API — 2 секунды (`USER_SERVICE_TIMEOUT`).
- Данные в памяти процесса: после перезапуска Users API снова два стартовых пользователя, заказов нет.

### 2.3. Ключевые точки интеграции (что обязательно покрыть сценариями)

1. Успешный межсервисный вызов при создании заказа.
2. Повторный запрос пользователя при чтении заказа.
3. Пользователь не найден → 404, побочных записей нет.
4. Users API недоступен → 503, заказ не сохраняется.
5. Авторизация на изменяющих операциях.
6. Валидация входных данных.
7. Время отклика межсервисного вызова.

## 4. Вариант партнёра и его сценарии

### 4.1. Требования варианта партнёра (Readers + Loans)

Типовой парный вариант той же архитектуры:

| Сервис | Назначение |
|---|---|
| Readers API | Читатели библиотеки: создание, получение по id, уникальный билет |
| Loans API | Выдача книги; перед записью запрашивает читателя в Readers API |

Поведение интеграции:

- успех: 201, в ответе вложенный `reader`;
- читателя нет: 404;
- Readers API недоступен: 503;
- выдача без токена: 401;
- невалидная дата возврата / пустое название книги: 422.

### 4.2. Сценарии партнёра (как были переданы)

**P-01. Успешная выдача книги**  
Создать читателя, затем `POST /loans` с его id. Ожидается 201 и поле `reader`.

**P-02. Выдача неизвестному читателю**  
`POST /loans` с `reader_id=0`. Ожидается ошибка.

**P-03. Сервис читателей выключен**  
Выключить Readers API, вызвать `POST /loans`. Ожидается 503.

**P-04. Список выдач**  
`GET /loans` после P-01. Ожидается непустой список.

**P-05. Пустое название книги**  
`POST /loans` с `book=""`. Ожидается 422.

### 4.3. Оценка сценариев партнёра

| Критерий | Оценка | Комментарий |
|---|---|---|
| Количество | Удовлетворительно | 5 сценариев есть, формально минимум выполнен. |
| Покрытие happy path | Частично | P-01 не фиксирует конкретные поля ответа (`id`, `title`, `due_date`) и заголовок `Location`. |
| Негативные интеграционные случаи | Слабо | P-02 использует `reader_id=0` — это скорее 422 валидации, чем 404 «читатель не найден». Интеграционный 404 не покрыт. |
| Недоступность зависимости | Частично | P-03 не проверяет, что выдача **не сохранилась** (повторный `GET /loans` должен быть пустым / без новой записи). |
| Авторизация | Не покрыта | Нет сценария 401 (нет заголовка / неверный токен). |
| Чтение с повторным вызовом | Не покрыто | Нет `GET /loans/{id}` — а это вторая точка интеграции. |
| НФТ / время отклика | Не покрыто | Нет проверки таймаута и SLO межсервисного вызова. |
| Трассировка | Не покрыта | Нет `X-Request-ID`. |
| Корректность шагов | Замечания | В P-02, P-04, P-05 не указаны токен, точные URL, тела и коды. P-04 зависит от P-01 — сценарии не изолированы. |
| Полнота ожидаемого результата | Недостаточная | Часто указан только код, без тела и заголовков. |

**Вывод по партнёру:** набор закрывает только «счастливый путь», грубую 503 и валидацию пустого поля. Не покрыты: 404 именно как ответ зависимости, идемпотентность ошибки (запись не создаётся), повторный fetch при чтении, авторизация, SLO, изоляция сценариев. Сценарии нужно переписать в том же формате, что в разделе 3, с конкретными URL, телами и проверками побочных эффектов.

Рекомендации партнёру:

1. Заменить P-02 на `reader_id=999999` и явный ожидаемый 404.
2. В P-03 добавить шаг `GET /loans` и проверку, что новой выдачи нет.
3. Добавить сценарии: 401, `GET /loans/{id}` с актуальным `reader`, время вызова Readers API, невалидный токен.
4. У каждого сценария — свои предусловия и тестовые данные, без жёсткой зависимости от предыдущего.

## 5. Рецензия на наши сценарии (раздел 3)

Та же сетка критериев применена к TS-01…TS-05. Это имитация оценки партнёра: те же пробелы, которые мы нашли у него, нельзя оставлять у себя.

| Замечание | Где | Почему это важно |
|---|---|---|
| Не проверено, что при 404/503 заказ **не записался** | TS-02, TS-03 | Интеграционный тест обязан ловить побочный эффект, а не только код ответа. |
| Нет проверки заголовков `Location`, `X-Request-ID`, `X-User-Service-Time-Ms` | TS-01, TS-04 | Они есть в требованиях. |
| Нет сценария на повторное чтение после создания и на список заказов | — | `GET /orders` тоже ходит в Users API на каждый элемент. |
| Нет 404 на несуществующий заказ | — | Нужно отличать «нет заказа» от «нет пользователя». |
| Нет валидации тела (422) и конфликта email (409) | — | Ключевые контрактные ошибки Users API. |
| Нет неверного токена, только отсутствие заголовка | TS-05 | В требованиях два разных 401. |
| Нет SLO по времени межсервисного вызова | — | Прямое НФТ-требование курса. |
| Нормализация email/имени не проверена | — | Иначе интеграция может сломаться на регистре email. |
| Предусловия и данные слишком общие | все | Сценарий должен быть воспроизводим без чтения кода. |
| TS-04 зависит от TS-01 | TS-04 | Сценарии лучше делать независимыми. |

Эти замечания — основание для раздела 6.

## 9. Выводы

1. **Свой вариант** — проект `user-order-services`: два FastAPI-сервиса с синхронным HTTP-вызовом. Это классическая постановка для интеграционного тестирования, задание на сценарии ложится на него напрямую.
2. Первая версия содержала 5 сценариев и закрывала happy path, 404, 503 и 401, но не проверяла побочные эффекты, заголовки, SLO, валидацию и изоляцию данных.
3. Сценарии партнёра (Readers + Loans) формально есть, но некорректны в деталях: `reader_id=0` вместо 404, нет проверки, что при 503 запись не создалась, нет 401 и повторного fetch. Их нужно дописать до того же уровня, что ITS-01…ITS-10.
4. После рецензии свои сценарии расширены до 10: добавлены побочные эффекты 404/503, SLO, оба варианта 401, 409, 422, различие 404 заказа и 404 пользователя, список заказов и трассировка.
5. Улучшенные сценарии совпадают с автотестами репозитория, их можно демонстрировать прогоном `make check`.

Если появится живой одногруппник с другим вариантом — в отчёт подставляются его 5 сценариев в раздел 4, а раздел 5 заменяется его письменной рецензией. Раздел 6 при этом уже готов как «исправленная версия».
